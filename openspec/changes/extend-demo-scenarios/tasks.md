- [ ] 2.2 Render the dialog via `renderer.createRoot(identity, { node: "view", viewId: "dialog", props: {} })` with the per-adapter `views: { dialog }` registry option.
- [ ] 2.3 Add a "Mount child" button that calls `renderer.mountChild(dialogRoot, "body", childIdentity, { kind: "section", attributes: { role: "child" }, children: [...], slots: {} })` (a small visible child, e.g. a paragraph of text and a nested button proving its own `registerInteraction` fires independently of the dialog's own listener) and an "Unmount child" button that calls `renderer.removeRoot(childRoot)`, toggling button enabled/disabled state so a visitor can only mount once at a time per dialog.
- [ ] 2.4 Make the isolation visible: register a `click` interaction on both the dialog root and the child root, each incrementing its own on-page counter, so a visitor can click inside the child and see only the child's counter move, then click the dialog's own chrome and see only the dialog's counter move.

## 3. Keyed list reordering scenario

- [ ] 3.1 Create `packages/demo/src/scenarios/keyed-list.ts` exporting `mountKeyedListScenario(label, makeRenderer, column)`: keep a local `Map<string, string>` of `key → currentValue`, seeded with each row's initial label. A `listOf()` helper builds `{ kind: "ul", attributes: {}, slots: {}, children: keys.map(key => ({ kind: "li", attributes: {}, children: [{ kind: "input", attributes: { value: values.get(key) } }], slots: {}, key })) }` reading from that map (not a static label), rendered via `renderer.createRoot`.
- [ ] 3.2 After each commit, attach a native `input` event listener to every row's `<input>` (or use one delegated listener on the `<ul>` container) that writes the typed value back into the `key → currentValue` map — this is the fix for a real bug an adversarial review caught: Solid/React both treat `input`/`textarea`/`select`'s `value` as controlled (`add-input-value-binding`), so a later commit unconditionally overwrites the DOM value from whatever the `RenderNode` says; without capturing edits into the map first, Shuffle would silently stomp anything a visitor typed.
- [ ] 3.3 Add a "Shuffle" button that permutes the key order and re-commits via `renderer.commit(root, identity, listOf(shuffledKeys))`, reading each key's value from the CURRENT map (not the original seed labels) — demonstrating each row's `<input>`, including whatever a visitor typed into it, moves with its key rather than staying at its old position.
- [ ] 3.4 No comparison "unkeyed" list is required — the contrast is implicit (a visitor who understands what "shuffle preserves my typed text" means has seen the mechanism); do not add a second unkeyed list purely to contrast, since that doubles the scenario's surface for no clearer payoff (avoid scope creep beyond what design.md calls for).
